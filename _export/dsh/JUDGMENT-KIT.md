# 判定工具箱（JUDGMENT-KIT）

> 与 harness 无关的方法：真源基准 → 判据脚本 → 判据锁 → 修订台账 → 状态矩阵。
> 这套东西解决的是同一个问题：**「看起来对」和「量出来对」之间那道缝。**
> 2026-11-01～02 在一个真实项目里跑了十几轮，代价是被骂了 6 次，规律是从那 6 次里抽的。

## 一、要解决的问题（真实事故，不是假想）

| 事故 | 表面现象 | 真因 |
|---|---|---|
| 卡片高度塌成 20px | 门禁全绿 | 用 `flex:1` 分配高度，而内容高为 0 |
| 卡片高 1264px | 门禁全绿 | 用 `aspect-ratio` 和 grid 行高互相撑 |
| 标题 18px（真机 20px） | 门禁全绿 | 基准抄的是**客户端**抓取件，不是管理端真机 |
| 「升级到 v4」不存在 | 无判据反应 | 状态与动作从未被定义，靠实现者当场记 |
| 为了演示图好看删掉线上断点 | 判据全绿 | 没有任何一条判据在看「列数」 |

**共同点：每一次都是「我改的」被当成了「对的」。** 判据量的是我自己写的契约，不是真源。

## 二、四件套

### 1. 真源基准文件（唯一事实来源）

```json
{
  "card": { "aspectRatio": "0.9 / 1", "borderWidth": 1, "borderColor": "#e5e7eb", "radius": 12 },
  "cover": { "padding": "12 12 8" },
  "title": { "fontSize": 20, "lineHeight": 30 },
  "_evidence": [
    "真机实测（1440 视口）：card 272.5×302.8 / cover 270.5×179.8 / title 20px",
    "★标题 20px 是真机量的：抓取件写 18px，那是客户端卡片"
  ]
}
```

- **必须带 `_evidence`**，逐条写「这个数是从哪一行 HTML / 哪次测量来的」。
  以后任何人（包括自己）想改回去，都得先改这个文件，而文件里写着依据。
- **格式要严格**：`"0.9 / 1"` 是字符串，写成数字 `0.88` 会让判据算出 NaN，
  而不是明确报「格式不对」—— 这种坑要写进字段注释。

### 2. 判据脚本（读文件，不写死数字）

```js
const METRICS = JSON.parse(fs.readFileSync('assets/card-metrics.json', 'utf8'));
ok('C6a 卡片宽高比＝基准', Math.abs(actual - parse(METRICS.card.aspectRatio)) <= 0.02,
   `卡 ${w}×${h}，宽高比 ${ar}（要 ${METRICS.card.aspectRatio}）`);
```

三条纪律：

- **正控**：每条断言都要能算出具体数值，不许只判「有没有」。
- **负控**：每条断言配一把「刀」——故意注入错误，验证它真的会红。
  负控返回「未量」= 这条没在量，比红更严重。
- **输出折叠**：默认只打失败项 + 一行汇总，`--verbose` 看全。

### 3. 判据锁（防止自己改自己）

- 锁文件存每个判据文件的**内容哈希**。
- 改了判据但没登记 → 跑闸直接 `rc=4`，不算通过。
- 重签必须带 `--by`，理由进台账。

### 4. 修订台账（`amendments.tsv`）

```
日期 \t 文件 \t 原来那条错在哪 \t 旧哈希 \t 新哈希 \t 重跑后rc
```

- 理由必须包含「原来漏了什么」的判断词（假绿 / 误报 / 过期 / 漏 / 退役）。
- 禁写不陈述事实的短语（「放宽」「优化一下」）—— 校验器会拒。
  这条不是文字洁癖：**「放宽」会把一次真实的判据失效说成一次风格调整。**

## 三、状态矩阵（治「动作和状态从没被定义」）

把「每种状态下每个动作该不该有、叫什么」写进 JSON：

```json
{
  "apps": {
    "states": {
      "已上架": { "power": "下架", "powerConfirm": true,
                 "menu": ["编辑应用","客户授权","版本管理","复制应用","导出应用","下架","删除应用"] },
      "未发布": { "power": null,
                 "menu": ["编辑应用","客户授权","版本管理","复制应用","导出应用","删除应用"] }
    }
  }
}
```

判据逐格核：每种状态各取一张卡，核对电源按钮有无与文案、⋮ 菜单项集合。
**改代码不改表立刻报错，新增状态忘了配也立刻报错。**

## 四、一条经验：拦截要在「超的当下」，不能在「事后复盘」

- 规则写进文档 = 提醒，迟早被跳过。
- 观测（记日志、写报告）= 发现了也没人挡。
- **拦截**（超预算当场被拒）= 唯一稳的。

判断一条规矩是否成立：**答不出「谁把路掐断」，就不算修好。**

## 五、代价

这套东西不便宜：每加一条判据要写正控 + 负控 + 修台账 + 重签，一次十几分钟。
**只在「改错了会被人一眼看出来」的地方用**：像素级复刻、状态机、金额/权限类逻辑。
不要给每个字段都配判据 —— 判据本身也会变成要维护的代码。
